A. SYSTEM ARCHITECTURE
----------------------------------------------------------------------
The system utilizes a lightweight, zero-latency desktop and cloud-deployable
monolith architecture:
1. Frontend Layer:
   - React 18 single-page application built with Vite and Tailwind CSS.
   - Client-side navigation routing (`dashboard`, `products`, `billing`, `udhaar`,
     `customers`, `suppliers`, `cashbook`, `reports`, `settings`).
   - Bundled and minified into `dist/assets/` and statically served by Express.
2. Backend Layer:
   - Node.js (v20+ / v24) runtime running Express HTTP server (`backend/index.js`).
   - RESTful API endpoints handling JSON payloads (`bodyParser.json({ limit: '10mb' })`).
   - Dual-environment execution: Standalone Windows desktop workstations and
     Linux cloud hosting via Phusion Passenger (`server.js`).
   - Defensive security middleware injecting HTTP headers (`X-Content-Type-Options: nosniff`,
     `X-Frame-Options: SAMEORIGIN`, `Content-Security-Policy`).
3. Database & Storage Layer:
   - SQLite 3 embedded database (`backend/database.sqlite`).
   - Document-store pattern: entity tables utilize `id TEXT PRIMARY KEY, data TEXT`
     storing stringified JSON documents.
   - Atomic sequence counter table: `counters (id TEXT PRIMARY KEY, value INTEGER)`.
   - Automated 6-hour scheduler saving snapshots into `backend/backups/`.

C. DATABASE SCHEMA MAP
----------------------------------------------------------------------
All tables exist in `backend/database.sqlite`:

1. `counters`
   - `id`: TEXT PRIMARY KEY ('invoiceNumber')
   - `value`: INTEGER (Current monotonic invoice integer)

2. `products`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: name, category, size, unit, stock, purchasePrice, retailPrice, shopId, supplierId, createdAt)

3. `customers`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: name, phone, address, balance, totalPurchased, totalPaid, createdAt, updatedAt)

4. `payments`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: customerId, saleId, amount, method, notes, date, createdAt)

5. `sales`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: invoiceNumber, type, total, amountPaid, initialPaid, remainingBalance, paymentType, customerName, customerPhone, customerId, shopId, items, createdAt, date)

6. `suppliers`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: name, contactPerson, phone, email, address, balance, totalPurchased, totalPaid, createdAt)

7. `purchases`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: supplierId, supplierName, totalAmount, paidAmount, remainingAmount, shopId, items, createdAt, date)

8. `supplierPayments`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: supplierId, amount, method, note, createdAt)

9. `expenses`
   - `id`: TEXT PRIMARY KEY (UUID)
   - `data`: TEXT (JSON: category, description, amount, shopId, paymentMethod, createdAt)

10. `stockTransfers`
    - `id`: TEXT PRIMARY KEY (UUID)
    - `data`: TEXT (JSON: sourceProductId, targetProductId, productName, quantity, sourceShopId, targetShopId, date)

----------------------------------------------------------------------
E. COMPLETE DATA FLOW
----------------------------------------------------------------------
1. Counter POS Sale:
   User builds Cart -> Selects Payment Mode -> Backend pre-validates stock ->
   Atomic `invoiceNumber` incremented -> Sale inserted into `sales` ->
   Physical stock decremented in `products` -> Customer debt incremented in `customers`
   (if credit) -> Upfront cash streams into `cashbook` -> Reports metrics updated.
2. Procurement Receiving:
   Manager enters vendor shipment in Purchases -> `purchases` record created ->
   Physical stock incremented in `products` -> Vendor Accounts Payable balance
   incremented in `suppliers` -> Upfront cash disbursement logged in `supplierPayments`
   -> Outflow registered in `cashbook`.
3. Customer Debt Settlement:
   Customer pays cash/bank installment -> Recorded in `payments` ->
   `customer.balance` decremented -> Open sales remaining balances reduced via
   targeted or FIFO allocation -> Inflow registered in `cashbook`.
4. Supplier Payment Settlement:
   Operator pays vendor -> Guard checks `balance > 0` and `amount <= balance` ->
   Recorded in `supplierPayments` -> `supplier.balance` decremented ->
   Outflow registered in `cashbook`.

----------------------------------------------------------------------
F. CROSS-MODULE BEHAVIOR
----------------------------------------------------------------------
All 7 modules interact synchronously:
- An Inventory transfer in Module 1 changes available stock in Module 2 (Billing).
- A Sale in Module 2 mutates Customer balance in Module 4 and triggers debtor
  ranking in Module 3 (Credit).
- A Purchase in Module 5 increases inventory in Module 1 and logs outflows in Module 6 (Cashbook).
- Operational expenses in Module 6 and line-item margins from Module 2 converge in
  Module 7 (Reports) for executive analytics.

----------------------------------------------------------------------
G. DATABASE RECONCILIATION
----------------------------------------------------------------------
Empirically verified across 69 executed test cases:
1. Customer Balance Parity:
   $$\text{Balance} = (\sum \text{Sales} - \sum \text{Returns}) - \sum \text{Payments} \quad (\text{Drift} = 0.00\text{ PKR})$$
2. Supplier Balance Parity:
   $$\text{Balance} = \sum \text{Purchases} - \sum \text{SupplierPayments} \quad (\text{Drift} = 0.00\text{ PKR})$$
3. Inventory Balance Parity:
   $$\text{Stock} = \text{Initial} + \text{Purchases} - \text{Sales} + \text{Returns} \pm \text{Transfers} \quad (\text{Delta} = 0)$$
4. Cashbook Register Parity:
   $$\text{Cash Balance} = \sum \text{Inflows} - \sum \text{Outflows} \quad (\text{Exact Parity})$$

----------------------------------------------------------------------
J. BUSINESS LOGIC FINDINGS
----------------------------------------------------------------------
- Open Furniture Pricing: Retail prices are flexible at counter checkout.
- Quotation Isolation: Non-binding quotes receive reference numbers but never
  modify physical stock, customer debt, or revenue figures.
- Sales Return Reversal: Returns invert inventory and debt symmetrically.
- Duplicate SKU Self-Healing: Startup reconciler detects and consolidates identical SKUs.

----------------------------------------------------------------------
K. SECURITY FINDINGS
----------------------------------------------------------------------
- Security Headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,

- Exploit Protection: Negative sales quantities and anonymous credit sales are

----------------------------------------------------------------------
L. BUGS AND ROOT CAUSES
----------------------------------------------------------------------
1. Quotation Phone Validation Bug:
   - Root Cause: Boolean grouping in `backend/index.js` checked `paymentType === 'Pending'`
     before quotation type.
   - Status: FIXED & VERIFIED ✅
2. Backend Missing Zero-Balance Supplier Lock:
   - Root Cause: Frontend button was disabled, but API route `POST /api/supplier-payments`
     lacked server-side check.
   - Status: FIXED & VERIFIED ✅
3. Backend Missing Overpayment Guard:
   - Root Cause: Allowed disbursing payments greater than outstanding vendor dues.
   - Status: FIXED & VERIFIED ✅
4. Reset Route Gating:
   - Root Cause: Checked client headers not sent by static frontend bundle.
   - Status: FIXED & VERIFIED ✅
