1. DATABASE ARCHITECTURE OVERVIEW
----------------------------------------------------------------------
The system utilizes SQLite 3 as an embedded document-store engine.
Tables (except `counters`) are created with the schema:
```sql
CREATE TABLE <table_name> (
    id TEXT PRIMARY KEY,
    data TEXT  -- stringified JSON document
);
```
Special Table:
```sql
CREATE TABLE counters (
    id TEXT PRIMARY KEY,
    value INTEGER
);
```

Active SQLite Tables (10 Tables):
1. `counters` (Manages invoice numbering sequences)
2. `customers` (Stores client profiles and credit balances)
3. `expenses` (Stores operating expenditures)
4. `payments` (Stores customer debt installment settlements)
5. `products` (Stores inventory catalog and branch stock)
6. `purchases` (Stores vendor procurement shipments)
7. `sales` (Stores counter sales invoices and line items)
8. `stockTransfers` (Stores inter-shop inventory movements)
9. `supplierPayments` (Stores vendor disbursements)
10. `suppliers` (Stores wholesale vendor profiles and AP liabilities)

5. ATOMICITY & TRANSACTION INTEGRITY ANALYSIS
----------------------------------------------------------------------
Findings on Multi-Table Operations:
- `POST /api/sales` performs multi-step sequential asynchronous database operations:
  1. `getNextInvoiceNumber()` (`UPDATE counters`)
  2. `insert('sales', ...)`
  3. `update('products', ...)` (for each line item)
  4. `update('customers', ...)` (if credit sale)
- Current Implementation:
  Uses sequential Promises. The controller pre-validates all stock and customer
  data BEFORE beginning writes. If validation fails, zero database writes occur.
- Architectural Recommendation (Milestone v2.1):
  Wrap all multi-table Express endpoints inside atomic SQLite transactions:
  ```javascript
  await dbRun('BEGIN IMMEDIATE TRANSACTION');
  try {
      // execute queries
      await dbRun('COMMIT');
  } catch (err) {
      await dbRun('ROLLBACK');
      throw err;
  }
  ```
  This guarantees that in the event of an unhandled Node.js crash during step 3,
  the invoice and counter will be rolled back cleanly.

6. DATA PERSISTENCE & DISASTER RECOVERY AUDIT
----------------------------------------------------------------------
1. Automated 6-Hour Database Snapshots:
   - Implementation: `ensureDailyBackup()` runs every 6 hours via `setInterval`.
   - Copies `database.sqlite` into `backend/backups/backup-YYYY-MM-DD.sqlite`.
   - Verification: Confirmed backup files present on disk with valid SQLite headers.
2. One-Click Manual Snapshots (`POST /api/backups/create`):
   - Instantaneous point-in-time snapshot with millisecond timestamp.
   - Verified creating valid, mountable copies of the active database.
3. In-App Database Restoration (`POST /api/backups/restore`):
   - Creates a `pre-restore-safety` backup before touching the live database.
   - Closes active SQLite connection handles cleanly.
   - Replaces `database.sqlite` with selected snapshot.
   - Re-runs `initDb()`, re-establishes connection pool, and executes `mergeDuplicateProducts()`.
   - Verified 100% operational with zero data corruption.
4. Administrative Reset Route (`POST /api/reset`):
   - Protected by `ALLOW_DB_RESET=true` environment variable and optional admin token.
   - Automatically takes a `pre-reset-safety` backup before executing any truncate.
