----------------------------------------------------------------------
1. MODULE PURPOSE
----------------------------------------------------------------------
The Billing (POS) module provides real-time retail counter sales checkout,
fast product cart assembly, dynamic price negotiation overrides, multi-tier
payment processing (Full Cash, Partial Down Payment, Pending Credit, Quotation),
sales return handling, automated sequential invoice numbering, immediate
inventory stock deduction, and automated customer debt accumulation.

----------------------------------------------------------------------
2. FEATURES FOUND
----------------------------------------------------------------------
- Fast cart building with item quantity adjustments and custom unit prices.
- Payment Status Modes:
  - Full: 100% upfront settlement, remaining balance = 0.
  - Partial: Upfront down-payment accepted; remainder accrued to customer debt.
  - Pending: Zero upfront payment; full invoice total debited to customer debt.
  - Quotation: Non-binding estimate; does not decrement stock or alter ledgers.
- Sales Returns (`type: 'Return'`): Inverts inventory stock (+1 piece restored)
  and reverses customer debt and purchase totals.
- Sequential Invoice Numbering: Monotonically incremental invoice numbers
  generated via the atomic `counters` table (`invoiceNumber`).
- Mandatory Customer Validation on Credit:
  - Strict rejection of generic "Walk-in Customer" when bill is on credit.
  - Mandatory customer phone number validation to ensure debt recoverability.
- Multi-Shop Context Switching: Checkout deducts stock only from the selected
  branch (`shop-1` vs `shop-2`).
- Inventory Stock Overdraft Protection: Rejects sales when item quantity exceeds
  available branch inventory.
- Inventory Stock Inflation Guard: Rejects non-positive line item quantities
  (blocking the negative sales exploit).
- Invoice Printing & Digital Receipt view.

----------------------------------------------------------------------
3. ACTUAL WORKFLOW
----------------------------------------------------------------------
1. Cashier selects branch context (Shop 1 or Shop 2).
2. Cashier searches items and adds to cart with negotiated counter prices.
3. Cashier selects customer (Walk-in or registered customer from directory).
4. Cashier selects Payment Type:
   - Full -> amountPaid equals invoice total.
   - Partial -> Cashier enters down payment amount. System requires registered
     customer name and phone.
   - Pending -> Cashier selects pending. System requires registered customer name and phone.
   - Quotation -> Non-binding estimate.
5. System pre-validates stock availability across all line items in the cart.
6. System generates next invoice number via `counters` table.
7. System commits invoice to `sales` table in SQLite.
8. System decrements physical product inventory in `products` table (if Sale).
9. If credit sale, system updates customer running `balance` and `totalPurchased`.

----------------------------------------------------------------------
4. UI FLOW
----------------------------------------------------------------------
- Component: Mounted at `currentPage === 'billing'`.
- Left Pane: Product catalog grid with category filters, search bar, stock badges,
  and quick-add buttons.
- Right Pane: Active Cart summary showing selected items, quantity controls, unit
  price inputs, item subtotals, invoice grand total, customer selection dropdown,

- Down-Payment Input: Appears when "Partial" is selected, dynamically displaying
  computed remaining debt.
- Complete Sale Button: Triggers form validation, sends `POST /api/sales`, opens
  invoice print preview modal with options to print receipt or start new bill.

----------------------------------------------------------------------
5. API FLOW
----------------------------------------------------------------------
- GET /api/sales -> Returns array of all recorded sales transactions.
- GET /api/sales/next-invoice -> Queries `counters` table (`id = 'invoiceNumber'`),
  returns `{ nextInvoiceNumber: current + 1 }`.
- POST /api/sales -> Accepts `{ items, total, customerDetails, shopId, type, date }`.
  1. Validates items is non-empty array with positive quantities and non-negative prices.
  2. If Partial or Pending (and not Quotation), validates non-empty `customerName`
     (rejecting 'Walk-in Customer') and non-empty `customerPhone`.
  3. Pre-validates physical stock availability for each item in the cart.
  4. Increments invoice number in `counters` table.
  5. Inserts sale record into `sales` table.
  6. Decrements product stock in `products` table (or increments if Return).
  7. Updates customer balance, totalPurchased, and totalPaid in `customers` table.
  8. Returns HTTP 201 with created sale payload.

----------------------------------------------------------------------
6. DATABASE TABLES USED
----------------------------------------------------------------------
- `sales`: Stores invoice header, line items, customer details, and payment status.
- `counters`: Manages monotonic `invoiceNumber` sequence.
- `products`: Physical stock decremented on sales, incremented on returns.
- `customers`: Debt balance, totalPurchased, and totalPaid updated on credit sales.

----------------------------------------------------------------------
7. DATABASE FIELDS INVOLVED
----------------------------------------------------------------------
`sales` table:
- `id`: UUID string.
- `data.invoiceNumber`: Sequential integer (#1, #2, #3, ...).
- `data.type`: 'Sale' | 'Return' | 'Quotation'.
- `data.total`: Number (invoice grand total).
- `data.amountPaid`: Number (cash received upfront).
- `data.remainingBalance`: Number (total - amountPaid).
- `data.paymentType`: 'Full' | 'Partial' | 'Pending'.
- `data.customerName`: String.
- `data.customerPhone`: String.
- `data.customerId`: UUID string (if registered customer).
- `data.shopId`: 'shop-1' | 'shop-2'.
- `data.items`: Array of objects:
  `[{ id, productId, name, quantity, price, total }]`.
- `data.createdAt` & `data.date`: Unix timestamp (ms).

`counters` table:
- `id`: 'invoiceNumber'
- `value`: Integer (last committed invoice number).

----------------------------------------------------------------------
8. DATABASE RELATIONSHIPS
----------------------------------------------------------------------
- `sales.customerId` -> `customers.id` (N:1)
- `sales.items[].productId` -> `products.id` (N:1)
- `sales.id` -> `payments.saleId` (1:N, for subsequent settlements)

----------------------------------------------------------------------
9. CREATE / UPDATE / DELETE OPERATIONS
----------------------------------------------------------------------
- CREATE: Atomic multi-table write affecting `counters`, `sales`, `products`,
  and `customers`.
- UPDATE: Subsequent customer debt settlement updates `remainingBalance`,
  `amountPaid`, and `paymentType` on open sales.
- DELETE: No front-desk sales deletion option in POS to preserve financial audit trail.

----------------------------------------------------------------------
10. BUSINESS LOGIC
----------------------------------------------------------------------
- Pre-Validation Guard: Validates that all items in cart have sufficient stock
  BEFORE modifying any database state. If item #3 of 5 has insufficient stock,
  the entire order is aborted; items #1 and #2 are NOT deducted.
- Quotation Segregation: Quotations receive invoice numbers for reference but do
  not decrement physical inventory or alter customer accounting balances.
- Return Inversion: Returns reverse both stock and financial debt.

----------------------------------------------------------------------
11. CALCULATIONS
----------------------------------------------------------------------
- Line Item Total:
  $$\text{Item Total} = \text{Quantity} \times \text{Price}$$
- Invoice Grand Total:
  $$\text{Grand Total} = \sum \text{Item Totals}$$
- Remaining Debt:
  $$\text{Remaining Debt} = \text{Grand Total} - \text{Amount Paid}$$
- Customer Balance Delta:
  $$\Delta \text{Balance} = \text{Remaining Debt} \quad (\text{positive for Sale, negative for Return})$$
